fix-order.txt
=============

Working order for the logs-to-spans OpenTelemetry connector, ahead of the
donation to opentelemetry-collector-contrib.

Repo:   https://github.com/agardnerIT/logs-to-spans-otel
Issues: https://github.com/agardnerIT/logs-to-spans-otel/issues

Three constraints drive the order:

  1. You cannot manually verify any later fix until the collector builds and
     the shipped example config validates. That is session 1.

  2. Three issues rewrite the same function (`addToGroup` in connector.go):
     #7, #11, #15. Sequence them and you get one clean refactor; parallelise
     them and you get three conflicting rewrites.

  3. The config surface must be frozen exactly once. #8 and the type-naming
     decision change it, and so do #1, #3, #11, #12, #13, #14. The donation
     issue asks for the full option list, and metadata.yaml /
     config.schema.yaml / the README config table must be written against a
     surface that has stopped moving. Hence the Phase 3 decision gate.

[3] #7  DONE - issue closed. Commit 1a1b6e7.
        Bug: stale timer can evict the live group and silently drop records
        https://github.com/agardnerIT/logs-to-spans-otel/issues/7

    Outcome: logGroup gained a `flushed` flag. flushGroup is a no-op for an
    already-flushed group, stamps `flushed` before touching anything, and only
    deletes the map entry when c.groups[key] == group. addToGroup's split path
    stamps `flushed` and stops both timers before removing the group from the
    map. The flag also kills the duplicate emission from the second of the two
    timers per group. Three tests added; the stale-callback one fails on the
    pre-fix code. go vet + go test -race clean; CI green (run 36704296493).

    Why here: silent record loss, small isolated fix, and it edits a function
    that #11 and #15 also edit.

    Core bug: Timer.Stop() returns false when the callback is already queued,
    so the old group's callback runs flushGroup(key, oldGroup), which does an
    unconditional `delete(c.groups, key)` - now pointing at the replacement
    group. The live group is orphaned, its records are lost, and the span-link
    chain breaks.

    Scope:
      - Guard the delete by identity: if c.groups[key] == group { delete }
      - Stop timers before mutating the map.
      - Optional: two time.AfterFunc per log record is heavy at volume;
        consider one reused timer per group.
      - context.Background() in the timer callbacks drops cancellation.

    Done when: a regression test covers the stale-callback path, no orphaned
    groups after a max_logs_per_trace split, `go test -race` passes.

[4] #8  DONE - decisions recorded, issue closed. Commit 51501af.
        Bug: unmatched_behaviour is dead config and pass_through is not
        implementable
        https://github.com/agardnerIT/logs-to-spans-otel/issues/8

    The field is declared, defaulted and validated but never read in
    connector.go. ConsumeLogs unconditionally `continue`s past unmatched
    records. And pass_through CANNOT work as documented: factory.go registers
    only connector.WithLogsToTraces, so there is no logs consumer and the
    connector cannot emit log records. Users choosing pass_through today get
    silent drops - the worst outcome for someone who picked it specifically
    to avoid data loss.

    DECIDED: delete the option. pass_through needs connector.WithLogsToLogs
    and a logs consumer - a second component identity that would make
    correctness depend on how the user wired the pipeline, and that duplicates
    what routingconnector already does. Filtering the stream up front with
    filterprocessor is the documented answer and the recipe already existed.
    Removing the key means strict decoding now rejects configs that set it
    ("'logs_to_spans.Config' has invalid keys: unmatched_behaviour"), which is
    the intended loud failure for a former no-op.

    ALSO DECIDED HERE - contributes to #17:
    Type naming. KEEP `logs_to_spans`. No user-facing rename.

    The original claim in this file was WRONG. Checked the metadata.yaml of
    every connector in contrib: the current convention is snake_case, and the
    concatenated names are the DEPRECATED aliases.

      directory                    type                deprecated_type
      servicegraphconnector        service_graph       servicegraph
      spanmetricsconnector         span_metrics        spanmetrics
      signaltometricsconnector     signal_to_metrics   signaltometrics
      metricsaslogsconnector       metrics_as_logs     metricsaslogs
      otlpjsonconnector            otlp_json           otlpjson
      roundrobinconnector          round_robin         roundrobin
      slowsqlconnector             slow_sql            slowsql
      grafanacloudconnector        grafana_cloud       grafanacloud
      count/routing/sum/failover/exceptions -> single word (no separator
      needed at all)

    So logs_to_spans already matches the convention (cf. signal_to_metrics,
    metrics_as_logs). Renaming to `logstospans` would pick exactly the shape
    contrib is migrating away from, and break every existing user's config.
    A "...processor" suffix is wrong outright: connectors are a distinct
    component kind, not processors.

    DIRECTORY convention is "type with underscores removed + connector":
    span_metrics -> spanmetricsconnector, signal_to_metrics ->
    signaltometricsconnector. So logs_to_spans -> connector/logstospansconnector.
    Only the directory/module move in #17 remains; the type string is settled.

    FROZEN CONFIG SURFACE - write metadata.yaml, config.schema.yaml and the
    README table against exactly this and nothing else:

      timeout, max_wait, max_logs_per_trace, group_by_keys, duration_keys,
      end_span_duration, service_name

    No unmatched_behaviour. Type string: logs_to_spans. Directory at donation:
    connector/logstospansconnector.

    Done when: both decisions are recorded on the issues, and the final config
    option list is written down.

[6] #14  DONE - issue closed. Commit b3d745c.
         Support extracting the group key from log attributes, not just the
         body
         https://github.com/agardnerIT/logs-to-spans-otel/issues/14

    searched in order. Precedence is defined as attributes first, then body:

    unmatched_dropped metric description updated accordingly.

    Tests: 9 new - extraction order, non-string attribute, empty-value
    fallthrough, attribute-over-body precedence for string and Map bodies,
    body fallback when the attribute is absent, attributes-only end-to-end
    grouping into two traces, and the three validation cases.

    README: rewrote "Key extraction" (three strategies, precedence, exact
    matching, stringified values), added the `group_by_attributes` reference
    row, removed "(required)" from `group_by_keys`, updated the example, the
    Unreleased changelog, the unmatched-filtering text, and rewrote the
    filelog option in "Grouping non k=v logs" to teach
    regex_parser + group_by_attributes instead of the old body-only caveat.

    Verified: go vet + go test -race clean; OCB working-tree build (replace

[7] #11  DONE - issue closed. Commit af101ac.
         Bound group cardinality (max_groups / TTL eviction) to prevent
         unbounded memory growth
         https://github.com/agardnerIT/logs-to-spans-otel/issues/11

    Outcome: new `max_groups` option (default 1000, 0 disables). When a log
    record opens a new group and the map already holds max_groups groups, the
    least recently updated group is flushed early and emitted as a trace
    before the new group is admitted. Ties are broken by key so eviction is
    deterministic. The victim is marked flushed and both timers stopped before
    it leaves the map, reusing the #7 retire-before-removal discipline, so an
    already-queued callback cannot re-emit it or delete a replacement. Only a
    NEW key can trigger eviction - adding records to a buffered group never
    evicts it, so a hot key is never split by the cap. Evicted records are not
    dropped, only re-bounded: the trace boundary moves earlier.

    Decision - no `group_ttl`. max_wait is already a hard TTL from the first
    log in a group; a separate TTL option would duplicate it. Documented
    instead of adding dead-ish surface.

    Two metrics, consuming #1's meter: `..._groups_evicted` (counter) and
    `..._active_groups` (observable gauge polled from len(c.groups) under the
    same mutex). The gauge is the operator's view of the bound; the counter
    is the eviction signal. No debug log per eviction - the counter is the
    durable signal and a per-eviction log would flood under high cardinality.

    Two latent bugs found and fixed while writing the tests:
      - the max_logs_per_trace split created its replacement group with a zero
        lastUpdated, which would have made every fresh replacement the first
        eviction victim. New group now gets time.Now().
      - replacement groups from a split need the same recency stamp as any
        other live group. Regression test asserts it is non-zero.

    Tests: 11 new. LRU choice, deterministic tie-break, 0=unlimited, no
    eviction on an existing key, every record survives eviction, stale-callback
    idempotency, split-replacement recency, groups_evicted counter,
    active_groups gauge, negative/zero validation. go vet + go test -race
    clean. OCB working-tree build + validate collector.yaml clean; end-to-end
    with max_groups: 1 reports groups_evicted 2 / traces_created 3, and the
    shipped example reports active_groups 0 after flush.

    Consumed the counters from #1. #15 (and #12's key construction) still
    follow and must build on this addToGroup shape.


[8] #12  Preserve source resource attributes and scope grouping by resource
         https://github.com/agardnerIT/logs-to-spans-otel/issues/12

    processGroup writes only service.name; host.name, k8s.pod.name,
    service.instance.id are all discarded. And grouping ignores the resource
    entirely, so two different pods both logging userID=123 merge into one

    Composes with #11's grouping change - consider doing the key construction

[9] #13  Link generated spans to the originating trace when log records carry
         trace context
         https://github.com/agardnerIT/logs-to-spans-otel/issues/13

    extractLogRecord reads only timestamp, duration, body and severity, so an
    incoming trace_id/span_id is thrown away. Without this, the traces are
    disconnected from the real traces they came from, which undercuts the
    whole legacy-migration use case. Small change, high value.


[10] #3  Configurable span naming instead of full log body
         https://github.com/agardnerIT/logs-to-spans-otel/issues/3

    Already scoped on the issue (span_name_template with {body} / {severity}
    / {truncated:N} ). Currently the span name is the entire log body - high
    cardinality and potentially multi-KB. Independent of everything else.


[11] #15  Move log record extraction out of the global mutex
         https://github.com/agardnerIT/logs-to-spans-otel/issues/15

    MUST come after #7 and #11 - all three edit addToGroup.

    extractLogRecord runs under c.mu, and for map/JSON bodies valueToString
    calls AsString(), which serialises the body to a string while holding a
    lock shared by all groups and timer callbacks. The connector is
    effectively single-threaded.

    Careful: the conversion must still be eager. plog.LogRecord is a
    reference into upstream-owned pdata and must not be retained past
    ConsumeLogs, since the connector correctly declares
    Capabilities{MutatesData: false}. Add a benchmark, before and after.

DOCUMENTATION - EVERY SESSION, NO EXCEPTIONS
===========================================

Undocumented behaviour is a bug. Every session must leave the docs true.
Nothing merges that a user can observe and cannot read about.

If it changed, it gets documented:

  - new or changed config key      -> README "Configuration > Reference" table
  - removed config key             -> delete the table row, fix the how-to
                                      section that taught it, and add a
                                      Changelog entry marked BREAKING
  - changed observable behaviour   -> the README section that describes it
    (timing, flushing, what gets
    dropped, error/validation text,
    span links, defaults)
  - anything new visible in the
    output (attribute, scope name,
    span kind, resource)           -> README "Produced spans" table
  - a bug fix a user could have
    hit                            -> README Changelog
  - a limitation or caveat you
    discover                       -> document it where the feature is
                                      described, and link the issue that
                                      will fix it

Where it goes:
  - README.md is the source of truth for users. The "Configuration >
    Reference" table and the "Produced spans" table are kept in sync with
    config.go and connector.go by hand.
  - README.md "Changelog" gets an entry per session. Add to or extend the
    "### Unreleased" heading; never invent a version number, tags are cut
    separately (see KNOWN GOTCHAS).
  - At donation time this all becomes metadata.yaml + .chloggen entries
    (#17). Do NOT create a .chloggen directory in this repo.

Honest escape hatch - a purely internal refactor with no observable change
needs no README edit, but you must say "no user-visible change" in the issue
comment. That makes it a decision, not an omission.

Test it before closing:
  - walk your own diff and ask, for each hunk, "where is this documented?"
  - run the example collector end to end and follow the README as if you had
    never seen the code
  - the config reference table has one row per field in config.go - check the
    count

KNOWN GOTCHAS - DO NOT REDISCOVER
=================================

Go toolchain:
  - go.mod declares `go 1.25.0`. The Go 1.25.0 LINKER cannot link
    filterprocessor v0.154.0: it fails with
    "relocation target ...WithConditionConverter... not defined".
    This is patch-specific and fixed by later 1.25 patches - go1.25.14 and
    1.26.x link it fine.
  - Therefore .github/workflows/ci.yaml pins `go-version: '1.25.x'` with
    `check-latest: true`. Do NOT switch it back to `go-version-file: go.mod`
    until go.mod's directive is bumped past 1.25.0 (that is part of #17).
  - OCB is at ~/tools/ocb (v0.154.0). Build/verify:
        ~/tools/ocb --config builder-config.yaml
        ./otelcol-dist/otelcol-logs-to-spans validate --config collector.yaml

Collector runtime:
  - Default telemetry binds localhost:8888, so two collectors cannot run at
    once: "binding address localhost:8888 ... address already in use".
    Kill leftovers with `pkill -9 -f otelcol-logs-to-spans`.
  - `cd x && ./binary ... &` backgrounds the SUBSHELL, so `kill $!` does not
    stop the collector. Use `( exec ./binary ... ) &` so $! is the real PID.
  - Time-to-first-trace needs ~10s (default timeout: 5s). The debug exporter
    then prints ResourceSpans blocks.

Release / config surface:
  - The Go module proxy caches versions immutably. NEVER move or re-create a
    tag that has already been fetched (do not retag v0.4.0). Cut a new patch
    version instead.
  - Only collector.yaml is a shipped example config now. If you add another
    *.yaml example, CI picks it up automatically.

CI verification (issue #18 - FIXED, commit eda3916):
  - builder-config.yaml now has
        replaces:
          - github.com/agardnerIT/logs-to-spans-otel => ../
    (path is relative to output_path ./otelcol-dist, so ../ is the repo root)
    and ci.yaml runs go vet ./... and go test -race -count=1 ./... before the
    OCB build. CI compiles the working tree and the tests gate the build.
  - Local working-tree build + config check:
        ~/tools/ocb --config builder-config.yaml
        ./otelcol-dist/otelcol-logs-to-spans validate --config collector.yaml
    Confirm otelcol-dist/go.mod contains the replace directive before trusting
    the binary; if it is missing you are testing the published tag.
